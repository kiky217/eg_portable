# Generic execution model

Evaluation Gateway (EG) is a portable, provider-neutral controller for tasks. It is not a project-specific executor or a root shell.

## Canonical installation

Install one gateway, one durable task and audit state, and the bundled trusted file worker. The active physical operations are **bounded reads, exclusive file creation and SHA-256-bound replacement** within the configured worker directory. No external process catalog or separate per-project worker is installed.

See [the operational SKILL](../../SKILL.md) and [the portable runbook](PORTABLE_RUNBOOK.md).

## Required sequence — including staging

1. **REGISTER:** Save the task, step order, preconditions and independent acceptance criteria before starting work.
2. **PRE:** Verify the current step and authorize the exact supported action.
3. **EXECUTE:** Dispatch the action once through the admitted worker; preserve its signed receipt and recover the original result if interrupted.
4. **POST:** Submit fresh evidence created after PRE, plus the exact receipt where an action occurred. EG independently verifies the result.
5. **ADVANCE:** Move to the next step only after VERIFIED. Mark the task SATISFIED only after all required steps and task-wide criteria pass.

A health check, successful command, test pass or completed external project does **not** retroactively verify a task. Staging is subject to the same PRE/POST gates.

## Historical compatibility

Older task records may contain effect-class and executor metadata that are retained for audit verification. Those historical names are not installation requirements or currently available worker capabilities. Do not deploy retired operator bootstrap, typed process adapters or signers merely because they appear in an old record or protocol reference.

**Boundary:** EG can block invalid task claims and withhold verification, but cannot physically stop actions performed with tools outside its controlled boundary. Integrations must route their physical work through the admitted path to be governed.

## Optional reusable process adapter — source candidate, not admitted by default

The default portable installation remains the **single canonical EG evaluator plus
the bundled file worker**. The new source-only optional modules
`tools/generic_bounded_process_adapter.py` and
`tools/generic_bounded_process_service.py` define **one reusable provider-neutral
E3 `bounded_process_run` worker per operator-provisioned environment**, not one
worker per application or task. Installing the package does **not** activate E3.

An independently appointed operator must provision and pin a signature-verifiable
profile manifest with a fixed root-owned executable SHA256, immutable arguments,
private non-root worker working directory, bounded CPU/runtime/output and exact
target prefix. The same approved profile can serve different registered tasks
without creating per-project Python modules or provider-specific executors.
Caller-selected shell commands, arguments, environment variables and shell
interpolation are unsupported.

Before dispatch, the worker requires a valid **independent** operator signature,
distinct pinned worker signer, signed short-lived HITL approval bound to the
action fingerprint, and the **existing canonical EG READY_TO_EXECUTE PRE**
whose signed high-effect pin matches the original worker key and approval nonce.
The private Unix socket requires a pinned independent controller UID; read-only
liveness challenges are signed under the existing adapter probe domain.
Intent is durably recorded before the bounded effect, and a signed execution
receipt is sealed only after a successful fixed-profile invocation. An
interrupted/ambiguous intent is not retried automatically. An independently
verified canonical POST and task-wide acceptance are still required.

These modules are **source implementation candidates**, not a declaration
that any production adapter was operator-provisioned, independently signed
or admitted. Their isolated non-root tests use disposable **test-only**
operator/HITL/worker keys. No test key authorizes production, no key is
generated by an agent as a substitute for external operator consent, and
historical shell cutovers must never be relabeled as EG process receipts.

Do not configure retired project-specific executors. The optional provider-neutral
module is distinct from those retired adapters and must not silently replace
or broaden the default file-only worker. Release/promotion requires explicit
operator provisioning, live trust-root and UID-pin verification, the complete
PRE/receipt/POST E2E proof, rollback and audit verification.
